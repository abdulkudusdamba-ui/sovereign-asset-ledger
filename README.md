# Sovereign Asset Ledger

SAL is a FastAPI service for registering assets, maintaining registry identity,
and tracking verification and review workflows.

## Run locally

```bash
python -m pip install -r requirements.txt
alembic upgrade head
uvicorn app.main:app --reload
```

For a fresh SQLite database:

```bash
DATABASE_URL=sqlite:////tmp/sal-codespaces.db alembic upgrade head
DATABASE_URL=sqlite:////tmp/sal-codespaces.db uvicorn app.main:app --reload
```

Install the test runner and run the complete automated test suite with:

```bash
python -m pip install pytest
pytest
```

Migration verification commands:

```bash
alembic heads
alembic upgrade head
alembic downgrade -1
alembic upgrade head
```

## Authenticated offline sync

Offline sync accepts an authenticated batch of up to 100 create operations at
`POST /offline-sync/batches`. The complete request body is limited to 1 MiB.
Each operation has its own result, so invalid or conflicting entries do not
prevent other entries in the batch from succeeding.

Supported `asset_type` values are `asset`, `land`, `vehicle`, `gold`, and
`diamond`. Payload fields are strictly validated against the corresponding
SAL record fields; unknown properties, invalid types, oversized strings,
non-finite numeric values, and missing required values are rejected. Gold is
the currently supported precious-metal record. The endpoint does not accept
updates, ownership transfers, approvals, client audit data, or evidence
uploads.

Every operation requires a UUID `operation_id`. The UUID is unique per
authenticated user. Repeating the same UUID and payload returns its original
result without creating another asset. Reusing that UUID with different data
is preserved as a conflict. Database uniqueness constraints also protect the
asset-specific identifiers: land parcel number, vehicle VIN and registration
number, gold serial number, and diamond certificate number.

Asset creation is restricted to authenticated users with the `admin` or
`registrar` role. Asset owners in submitted payloads are claims, not
authoritative ownership records. SAL registry identity is generated by the
server, with verification and registry status left pending; land approval
also remains pending. Offline creation does not generate certificates or
QR-code artifacts and does not accept verification evidence. Reviewers should
use SAL's existing verification process before treating a submission as
verified.

Example request (the user must have an admin or registrar role):

```http
POST /offline-sync/batches
Content-Type: application/json
```

Send the access token returned by `POST /users/login` as a bearer token in
the `Authorization` header.

```json
{
  "operations": [
    {
      "operation_id": "a4efb4ae-35ce-4f86-9450-9d1aebbd81be",
      "operation": "create",
      "asset_type": "land",
      "data": {
        "parcel_number": "PARCEL-2026-0042",
        "owner_name": "Claimed owner",
        "community": "North Ridge",
        "district": "Central",
        "region": "Ashanti",
        "size": 2.5,
        "land_use": "Residential",
        "estimated_value": 125000.0
      }
    }
  ]
}
```

Vehicle payloads use `owner`, `registration_number`, `vin`, `manufacturer`,
`model`, `year`, `engine_number`, `color`, `estimated_value`, and optional
`chassis_number`. Gold payloads use `owner`, `type`, `purity`, `weight`,
`estimated_value`, and `serial_number`. Diamond payloads use `owner`,
`gemstone`, `carat`, `cut`, `color`, `clarity`, `certificate_number`, and
`estimated_value`. Generic assets use `owner`, `asset_name`, and `value`.

Example response:

```json
{
  "results": [
    {
      "operation_id": "a4efb4ae-35ce-4f86-9450-9d1aebbd81be",
      "asset_type": "land",
      "status": "created",
      "record_id": 17,
      "sal_id": "SAL-0123456789ABCDEF01234567",
      "ownership_status": "UNVERIFIED",
      "conflict_id": null,
      "message": "Asset submission recorded; ownership and verification remain pending"
    }
  ]
}
```

Result statuses include `created`, `rejected`, and `conflict`. Authenticated
users can list only their own conflicts at `GET /offline-sync/conflicts`;
administrators can review all conflicts. Only admins can resolve a conflict
using `POST /offline-sync/conflicts/{id}/resolve` with either
`{"resolution":"reject_submission"}` or
`{"resolution":"acknowledge_existing"}`. Resolution preserves the original
submission and does not modify an existing asset or approve ownership.

Operation payloads and conflicting submissions are retained for idempotency
and authorized review. They are not copied into audit-event metadata or
client-facing error messages. Existing authentication must remain valid when
the batch is synchronized; this project does not implement a mobile or
device-side offline queue.

## Limitations

- Offline sync currently supports creation only for the five asset types
  listed above. Other specialized SAL models are not accepted.
- There is no device-bound credential, client-side queue, offline evidence
  upload, automatic conflict merge, or background retry worker.
- A conflict acknowledgement is a review outcome only; it never makes a
  submitted owner authoritative and never overwrites the matching record.
